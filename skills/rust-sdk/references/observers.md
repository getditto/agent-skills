## CAP-11 Observers, diffing and back-pressure

```text
Store::register_observer<Q, F>(&self, query: Q, on_change: F) -> Result<Arc<StoreObserver>, DittoError>
  where F: FnMut(QueryResult) + Send + Sync + 'static
Store::register_observer_with_signal_next<Q, F>(&self, query: Q, on_change: F) -> Result<Arc<StoreObserver>, DittoError>
  where F: FnMut(QueryResult, Box<dyn FnOnce() + Send>) + Send + Sync + 'static
```

`StoreObserver` has `cancel()`, `is_cancelled()`, `query_string()` and
`query_arguments()`. There is no `Stream` API: bridge with a channel
([tokio.md](tokio.md#observer-to-async-consumer-with-back-pressure)).

## Delivery semantics

Executed on 5.0.4–5.2.0:

- **An initial callback arrives without any write**, after `register_*` returns, carrying
  the current result (possibly empty).
- Callbacks for one observer never overlap.
- The query must be a `SELECT`: anything else fails at registration with
  `CoreApi(DqlUnsupported)` "non-SELECT statement in store observer".
- The observer runs until `cancel()` or Ditto shutdown. **Dropping the `Arc` does not
  stop it** ([lifetimes.md](lifetimes.md#drop-does-not-cancel-observers-or-subscriptions)).
- An observer sees local changes, including those synced in from peers. It does not
  pull data from peers: pair it with a subscription for that ([sync.md](sync.md)).
- Arguments work as in `execute`: `register_observer((query, json!({ … })), …)`.

## Back-pressure with `signal_next`

`register_observer` signals readiness for you when the callback returns.
`register_observer_with_signal_next` hands you the signal instead:

- Until you call it, Ditto pauses deliveries for that observer while it keeps applying
  changes to the store.
- When you call it, Ditto delivers **at most one** callback with the latest result, and
  only if that differs from the last one delivered (executed: 20 inserts while the signal
  was held produced one callback with all 20 rows).
- **If you drop it without calling it, the observer never delivers again** — no error,
  no log (executed). Every early `return` path must call it, which is why the
  [tokio.md](tokio.md#observer-to-async-consumer-with-back-pressure) bridge wraps it in a
  type whose `Drop` calls it.
- It is `Send + 'static`: you may move it to another thread or task and call it after
  `.await`ed work — the main reason to use this form.

## Diffing

`dittolive_ditto::dql::Differ` computes index-based diffs between consecutive results,
identifying documents by `_id`:

<!-- snippet: rust-differ -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```rust
use std::sync::Mutex;

use dittolive_ditto::dql::Differ;

fn observe_changes(
    store: &Store,
) -> Result<std::sync::Arc<dittolive_ditto::store::StoreObserver>, DittoError> {
    // One Differ per observer: it remembers the previous result. Its first diff reports
    // every row as an insertion.
    let differ = Mutex::new(Differ::new());
    store.register_observer("SELECT * FROM orders ORDER BY _id", move |result| {
        let Ok(differ) = differ.lock() else { return };
        let diff = differ.diff(result.iter());
        println!(
            "+{} -{} ~{} moved {}",
            diff.insertions.len(),
            diff.deletions.len(),
            diff.updates.len(),
            diff.moves.len()
        );
    })
}
```
<!-- /snippet -->

- One `Differ` per observer: it is stateful. Its first `diff` reports every row as an
  insertion.
- `Diff` fields are `HashSet<usize>`s: `insertions` and `updates` index into the new
  result, `deletions` into the previous one; `moves` is `HashSet<DiffMove { from, to }>`.
- `diff` takes `&self`, but the callback is `FnMut` and must be `Sync`: wrap the
  `Differ` in a `Mutex` as above, or move the decoded rows to async code and diff there.
- Use `ORDER BY` so indices are meaningful.

## Choosing a form

| Need | Use |
|---|---|
| Latest value for a UI model or status endpoint | `register_observer` + `watch::send_replace` |
| Async processing of each state, slow consumer | `register_observer_with_signal_next` + the `Update`/`Ack` bridge |
| Insert/delete/move events for a list view | either form + `Differ` |
| One-off read | `store().execute`, not an observer |

Register few, broad observers rather than one per item: each observer re-runs its query
when relevant documents change. Architectural trade-offs:
[best-practices.md](../best-practices.md#observers).

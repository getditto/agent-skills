## CAP-01 Prerequisites, toolchain, package install

```bash
cargo add dittolive-ditto                      # resolves the latest stable release
cargo add tokio --features macros,rt-multi-thread,sync,time
cargo add serde --features derive
cargo add serde_json anyhow
```

Use the version `cargo add` resolves (or the project's existing `Cargo.lock`), not
5.2.0 by habit: 5.2.0 is this skill's knowledge baseline. Check release notes when the
resolved version is newer: <https://docs.ditto.live/sdk/latest/release-notes-hub/rust>.
`dittolive-ditto` pins `dittolive-ditto-sys` with `=`, so the two always move together.

Requirements:

- **rustc 1.91.0–1.97.x** — `rust-version = "1.91"`, and 1.98+ cannot compile the sys
  crate. Pin it: [below](#the-toolchain-pin).
- **`curl` on `PATH` and network access to `software.ditto.live` at build time**, unless
  the library is supplied locally ([below](#the-native-library)).
- **On Linux, a linker flag** — without it no binary links ([below](#linux-the-link-fix)).
- **A supported target** ([below](#supported-targets)).
- `serde` (with `derive`) and `serde_json` for documents and query arguments.

## The toolchain pin

Every published `dittolive-ditto-sys` from 4.14.7 to 5.2.0 fails on rustc 1.98 and newer
(executed on 1.98.0 and 1.99.1):

```text
error[E0690]: transparent struct needs at most one non-trivial field, but has 2
   --> …/dittolive-ditto-sys-5.2.0/dittoffi.rs:396:1
```

Executed on 5.2.0: 1.91.0, 1.94.0, 1.96.0 and 1.97.0 build. The prebuilt static library
reports `lib_rustc_version: rustc 1.91.0`, and the build script warns "Mismatch found
between toolchain used for the Ditto static libarary and the end-user Rust app, this can
cause linker issues on some targets" for any other version, so **1.91.0 is the
recommended pin**. Commit it at the workspace root:

```toml
# rust-toolchain.toml
[toolchain]
channel = "1.91.0"
```

rustup honours this only for the `cargo` it manages. A Homebrew or distro `cargo` earlier
on `PATH` ignores it — the build log line `app_rustc_version: … (Homebrew)` gives it away.
Re-check the window when you upgrade Ditto.

## Linux: the link fix

`libdittoffi.a` contains its own compiled copy of Rust's standard library. macOS's linker
tolerates the duplicate symbols; Linux linkers do not. Without the flag below, **every**
binary that depends on `dittolive-ditto` fails to link on Linux (executed for 5.2.0 on
x86_64 and aarch64, debug and release, with rustc 1.91.0 — the library's own compiler;
4.14.7–5.1.0 ship the same static-library packaging, and 4.14.7 was executed on x86_64
with the flag):

```text
x86_64 (rust-lld): rust-lld: error: duplicate symbol: __rustc::rust_panic
aarch64 (GNU ld):  multiple definition of `std::io::error::Error::new'
```

Commit this as `.cargo/config.toml` at the workspace root (Ditto's own CI links its
Linux artifacts with the same flag):

<!-- snippet: rust-linux-link-fix -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```toml
# libdittoffi.a carries its own copy of Rust's std. On Linux, GNU ld ("multiple definition
# of `std::io::error::Error::new'") and rust-lld ("duplicate symbol: __rustc::rust_panic")
# both reject the duplicates; macOS's linker accepts them. Ditto's own CI links this way.
[target.'cfg(target_os = "linux")']
rustflags = ["-C", "link-arg=-Wl,--allow-multiple-definition"]
```
<!-- /snippet -->

Switching to `-fuse-ld=lld` does not help. If you also set `RUSTFLAGS` in CI, it
*replaces* `target.<cfg>.rustflags`, so add the flag there too.

## Cargo features

| Feature | Default | Effect in 5.2.0 |
|---|---|---|
| `timeseries` | yes | pulls in `chrono`; no public API uses it |
| `preview-datastreams` | no | enables `ditto.datastreams()` — [preview.md](preview.md) |
| `preview` | no | enables the `preview` module (implied by the above) |
| `fs-storage`, `in-memory-storage` | no | forwarded to the sys crate, which ignores them: there is **no in-memory store** |
| `__ditto_multicast_beta`, `__internal-testing` | no | Ditto-internal; do not enable |

`default-features = false` is safe and drops `chrono`. Source: `Cargo.toml` and
`dittolive-ditto-sys` `Cargo.toml` of the 5.2.0 crates.

## The native library

`dittolive-ditto-sys`'s build script links `libdittoffi` (a closed-source C-ABI build of
Ditto's core). Its search order (`build/main.rs` in the 5.2.0 sys crate):

1. `$DITTOFFI_SEARCH_PATH` (a directory; absolute path recommended)
2. the current directory
3. `target/<profile>` and `target/<profile>/deps`
4. `$OUT_DIR`
5. otherwise download
   `https://software.ditto.live/rust/Ditto/<version>/<target>/release/libdittoffi.a`
   with `curl` into `$OUT_DIR`

The download is large (5.2.0: 110 MB for `aarch64-apple-darwin`, 196 MB for
`x86_64-unknown-linux-gnu`) and repeats after `cargo clean` or in a fresh `target/`.
Build-script environment variables:

| Variable | Meaning |
|---|---|
| `DITTOFFI_SEARCH_PATH` | directory holding `libdittoffi.a` (or the dylib) |
| `DITTO_LOCAL_BUILD=1` | never download; fail if not found |
| `LIBDITTO_STATIC=0` | link dynamically (default: static). You then own runtime lookup (rpath, `LD_LIBRARY_PATH`, `DYLD_FALLBACK_LIBRARY_PATH`) |

Failure strings: a missing library prints the warning ``[dittolive-ditto-sys]
`libdittoffi.a` not found (build with `-vv` to debug the locations searched)`` and
then attempts the download. A failed download panics with "Failed to download Ditto SDK
binary component". Under rust-analyzer the build script skips itself, so IDE checks work
offline.

Static linking is the default and the recommended form: one self-contained binary. On
Apple targets the build adds `Security` and `SystemConfiguration`; no other system
libraries are linked explicitly.

## Supported targets

Prebuilt libraries on `software.ditto.live` (executed: HTTP status per URL, 2026-11-15):

| Target | 4.14.7 | 5.0.4 | 5.1.0 | 5.2.0 |
|---|---|---|---|---|
| `aarch64-apple-darwin` | yes | yes | yes | yes |
| `x86_64-apple-darwin` | yes | no | no | no |
| `x86_64-unknown-linux-gnu` | yes | yes | yes | yes |
| `aarch64-unknown-linux-gnu` | yes | yes | yes | yes |
| Windows, iOS, Android, `*-linux-musl` | no | no | no | no |

The Rust SDK is a desktop/server SDK in practice. Mobile apps use the Swift or Kotlin SDKs.
Static musl builds are not possible. Docker images need a glibc base such as
`debian:bookworm-slim`, not `alpine`.

## CAP-02 Platform permissions, entitlements, build config

There are no manifests or entitlements: the Rust SDK targets Linux and macOS processes.
What you configure is the host:

- **LAN discovery** uses mDNS (UDP 5353) and then TCP connections on ports Ditto picks
  at runtime: allow them in host or container firewalls, or fix a listener port in
  `listen.tcp`. In containers, use host networking or give each peer a
  routable address and configure `connect.tcp_servers` ([transports.md](transports.md)).
- **Bluetooth LE on Linux** needs BlueZ and permission to use the adapter; see
  <https://docs.ditto.live/sdk/latest/deployment/bluetooth-on-linux>. Not verified here.
- **macOS**: a sandboxed app needs the network client/server entitlements; a plain CLI
  binary needs nothing. The local-network privacy prompt applies to GUI apps.
- **Persistence directory** must be writable and not shared with another running
  instance ([connect.md](connect.md#persistence-directory)).

Why a radio needs a given permission is `ditto-mesh-networking`'s topic (otherwise
<https://docs.ditto.live/sdk/latest/sync/customizing-transport-configurations>).

## CI recipe

Cache the downloaded library rather than re-downloading 100–200 MB per job, and make the
toolchain explicit:

```bash
# Fetch once per Ditto version and target, then point the build script at it.
version=5.2.0 target=x86_64-unknown-linux-gnu
mkdir -p "$HOME/.cache/ditto/$version/$target"
curl -fsSL -o "$HOME/.cache/ditto/$version/$target/libdittoffi.a" \
  "https://software.ditto.live/rust/Ditto/$version/$target/release/libdittoffi.a"
export DITTOFFI_SEARCH_PATH="$HOME/.cache/ditto/$version/$target"
export DITTO_LOCAL_BUILD=1   # fail fast instead of downloading again
rustup toolchain install 1.91.0 --profile minimal
cargo build --locked
```

Executed: with the library pre-fetched, the build links it without a download. With a
wrong path it fails fast: "Unable to canonicalize path given at DITTOFFI_SEARCH_PATH",
then "Failed to find `libdittoffi.a` in local search paths and DITTO_LOCAL_BUILD is set
to non-zero value, exiting." Key the cache on the `dittolive-ditto-sys` version in
`Cargo.lock`. Tests need an
offline license in the environment ([testing.md](testing.md)).

## CAP-18 Testing

There is no in-memory store and no mock: tests run the real SDK against a real
directory. One `Ditto` per test, each in its own temporary directory. The block is
generated from a test file that CI runs:

<!-- snippet: rust-test-harness -->

```rust
/// One Ditto per test, in its own directory. Fields drop in declaration order: `ditto`
/// comes first so the TempDir outlives it.
struct TestPeer {
    ditto: Ditto,
    _dir: tempfile::TempDir,
}

async fn test_peer() -> TestPeer {
    let dir = tempfile::tempdir().expect("temp dir");
    let config = DittoConfig::new(
        "my-app-tests",
        DittoConfigConnect::SmallPeersOnly { private_key: None },
    )
    .with_persistence_directory(dir.path());
    let ditto = Ditto::open(config).await.expect("open");
    ditto
        .set_license_from_env("DITTO_OFFLINE_LICENSE")
        .expect("set DITTO_OFFLINE_LICENSE");
    TestPeer { ditto, _dir: dir }
}

#[tokio::test]
async fn upsert_is_idempotent() {
    let peer = test_peer().await;
    let store = peer.ditto.store();
    for _ in 0..2 {
        store
            .execute((
                "INSERT INTO cars DOCUMENTS (:car) ON ID CONFLICT DO UPDATE",
                json!({ "car": { "_id": "c1", "make": "Toyota" } }),
            ))
            .await
            .expect("upsert");
    }
    let count = store
        .execute("SELECT * FROM cars")
        .await
        .expect("select")
        .item_count();
    assert_eq!(count, 1);
}
```

Dev-dependencies: `tempfile = "3"` and `tokio` with `macros`. Put the offline license in
the test environment (CI secret), never in the repository. Small-peers-only mode with
`private_key: None` needs no network.

## A failing assertion aborts the binary

Once any test in a binary has opened Ditto, Ditto's panic hook turns **every** panic in
that process into `abort()` (executed). A failing `assert!` therefore:

- kills the whole test binary with SIGABRT, so later tests in it never run, and
- prints `ERROR tracing_config: Panic: assertion … failed` plus the `left`/`right`
  values, then `Process aborting due to panic`, instead of libtest's summary.

Mitigations, in order of preference:

1. **Run tests with `cargo nextest run`.** nextest runs each test in its own process, so
   an abort fails one test and the rest still report.
2. Make assertions report before they panic: `assert_eq!` output is still printed, so
   read the log above the abort line.
3. Keep Ditto-using tests in their own integration-test binaries (`tests/*.rs`), away
   from pure unit tests, so an abort does not take unrelated tests down.

Installing your own `std::panic::set_hook` in a test after `Ditto::open` restores normal
unwinding for the test's own assertions (executed), but not for panics inside Ditto
callbacks.

## Harness rules

- **Use a unique directory per test.** Tests run in parallel threads by default, and two
  instances on one directory fail with `LockedDittoWorkingDirectory`.
- **Keep the `TempDir` alive at least as long as the `Ditto`**: hold both in one struct,
  with the `Ditto` field declared first (fields drop in declaration order).
- Use `#[tokio::test]`; a multi-thread flavour (`flavor = "multi_thread"`) is closer to
  production. Observer callbacks arrive on Ditto threads, so they work under either.
- **Wait for observers with a timeout, not a sleep:** `tokio::time::timeout(d,
  watch_rx.wait_for(..))`. Waiting is fine to time out; it is the *SDK* futures that
  must not be cancelled ([concurrency.md](concurrency.md#cancellation-safety)).
- Expect the initial observer callback: the first value is the current state, possibly
  empty.
- `dittolive_ditto::fs::TempRoot` exists, but `tempfile::TempDir` is the conventional
  choice; the SDK's `doctest_helpers` are behind a private feature.
- Two-peer tests in one process: open two instances on two directories, give one a
  `listen.tcp` port on `127.0.0.1` and the other `connect.tcp_servers`, and disable LAN
  discovery to keep the test hermetic. Not exercised by this skill's suite.
- More: <https://docs.ditto.live/sdk/latest/deployment/testing>.

## Testing behaviour that ends in an abort

To assert that something aborts (or hangs), re-run the test binary on itself in a child
process and inspect the exit status. The child reports through its exit code, because
its stdout is not reliable:

```text
std::process::Command::new(std::env::current_exe()?)
    .args(["--exact", NAME, "--nocapture", "--test-threads=1"])
    .env("CHILD", NAME)            // the test body checks this and runs the probe
    .status()?                      // ExitStatusExt::signal() == Some(6) for SIGABRT
```

Add a watchdog thread that calls `std::process::exit(code)` after a few seconds, so
that a hang becomes an exit code.

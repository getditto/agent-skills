## The model in one paragraph

Ditto is a C library with a Rust façade. It runs its own threads; it does not run on
your executor. Observer, presence, disk-usage, log and attachment-fetch callbacks are
**synchronous closures invoked on Ditto-owned threads that have no Tokio context**
(`Handle::try_current()` is `Err`; observer threads are named `live query callback N`).
The `async fn`s are a mix: `Ditto::open`, `Store::transaction*`, `Transaction::execute`
and `DittoLogger::export_to_file` await a completion callback; `Store::execute` and
`new_attachment*` are `async` wrappers around a synchronous FFI call that completes
inside the first `poll`. None of them needs a Tokio runtime — the SDK's own tests drive
them with `futures::executor::block_on` — but Tokio is the expected host.

So the integration rule is: **callbacks only hand data over; async code does the
work.** Never `.await`, block on I/O, take a contended lock, `tokio::spawn`, or panic in
a callback.

## Cancel-on-drop guard

`StoreObserver` and `SyncSubscription` keep running after the last `Arc` is dropped
(executed: an observer bound with `let _ =` still fires and stays registered). A guard
gives them ordinary RAII semantics, which is what Rust code around them assumes:

<!-- snippet: rust-cancel-guard -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```rust
use std::sync::Arc;

use dittolive_ditto::{store::StoreObserver, sync::SyncSubscription};

/// Ditto's handles keep running when the last `Arc` is dropped; only `cancel()` stops
/// them. `Cancelling` restores RAII: dropping the guard cancels the handle.
pub trait Cancel {
    fn cancel(&self);
}

impl Cancel for StoreObserver {
    fn cancel(&self) {
        StoreObserver::cancel(self);
    }
}

impl Cancel for SyncSubscription {
    fn cancel(&self) {
        SyncSubscription::cancel(self);
    }
}

#[must_use = "dropping the guard cancels the handle immediately"]
pub struct Cancelling<T: Cancel>(Arc<T>);

impl<T: Cancel> Cancelling<T> {
    pub fn new(handle: Arc<T>) -> Self {
        Self(handle)
    }
}

impl<T: Cancel> std::ops::Deref for Cancelling<T> {
    type Target = T;
    fn deref(&self) -> &T {
        &self.0
    }
}

impl<T: Cancel> Drop for Cancelling<T> {
    fn drop(&mut self) {
        self.0.cancel();
    }
}
```
<!-- /snippet -->

Store guards in the struct that owns the feature (a screen model, a service, a task's
locals); the feature's teardown then cancels them. `#[must_use]` turns the
`let _ = Cancelling::new(..)` mistake into a warning.

## Observer to async consumer, with back-pressure

`register_observer_with_signal_next` pauses delivery until `signal_next` is called;
changes that arrive meanwhile are coalesced into **one** later callback carrying the
latest result. Sending `signal_next` along with the data lets the async consumer pace
Ditto. Wrapping it in a type whose `Drop` calls it makes forgetting impossible — an
uncalled, dropped `signal_next` stops the observer forever (executed). Requires the
guard above:

<!-- snippet: rust-observe-channel -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```rust
use dittolive_ditto::prelude::*;
use serde::de::DeserializeOwned;
use tokio::sync::mpsc;

/// One observer delivery. Ditto sends nothing newer until this value is dropped, so a
/// slow consumer gets the latest state instead of a backlog.
pub struct Update<T> {
    pub items: Vec<T>,
    _ack: Ack,
}

struct Ack(Option<Box<dyn FnOnce() + Send>>);

impl Drop for Ack {
    fn drop(&mut self) {
        if let Some(signal_next) = self.0.take() {
            signal_next(); // never leave Ditto waiting: an uncalled signal stalls the observer
        }
    }
}

/// Observes `query` and delivers decoded rows to async code through a channel.
pub fn observe<T, Q>(
    store: &Store,
    query: Q,
) -> Result<(Cancelling<StoreObserver>, mpsc::Receiver<Update<T>>), DittoError>
where
    T: DeserializeOwned + Send + 'static,
    Q: IntoQuery,
    Q::Args: serde::Serialize,
{
    // Capacity 1 suffices: Ditto waits for the Ack before the next callback.
    let (tx, rx) = mpsc::channel(1);
    let observer =
        store.register_observer_with_signal_next(query, move |result, signal_next| {
            // Runs on a Ditto thread: decode here, never block, never panic.
            let items = result
                .iter()
                .filter_map(|item| item.deserialize_value::<T>().ok())
                .collect();
            let update = Update {
                items,
                _ack: Ack(Some(signal_next)),
            };
            // If the receiver is gone the update is dropped here, which acks it.
            let _ = tx.try_send(update);
        })?;
    Ok((Cancelling::new(observer), rx))
}
```
<!-- /snippet -->

Consume it in a task: `while let Some(update) = rx.recv().await { … }` — the update is
acked when it goes out of scope at the end of the loop body. Executed: with the consumer
holding the first update while ten inserts land, the next delivery is a single update
with all ten rows. `filter_map(.ok())` drops rows that do not match `T`; log them
instead if schema drift matters to you. To use the rows as a `Stream`, wrap the receiver
in `tokio_stream::wrappers::ReceiverStream`.

## Latest value only: `watch`

When the consumer only ever wants the current state (a UI model, a health endpoint),
`register_observer` plus `tokio::sync::watch::Sender::send_replace` is the simplest
correct form: it never blocks and never fails, and readers see the newest value. This
is what [`examples/minimal-app.md`](../examples/minimal-app.md) does. Decode inside the
callback and send the decoded value, not the `QueryResult`.

## Heavy queries off the async workers

`store().execute(..).await` runs the whole query inside its first poll, on the worker
thread polling it (executed: the future is `Ready` on first poll, and an un-awaited
future does nothing). On a multi-thread runtime a quick point lookup is harmless; a
large scan, a bulk `INSERT` of thousands of documents, or anything on a
`current_thread` runtime stalls every other task on that thread for its duration:

<!-- snippet: rust-heavy-query -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```rust
/// `Store::execute` does its work inside the first poll, on the polling thread. Move
/// large scans and bulk writes off the async workers.
pub async fn count_off_the_runtime(store: Store, query: String) -> anyhow::Result<usize> {
    let runtime = tokio::runtime::Handle::current();
    let result =
        tokio::task::spawn_blocking(move || runtime.block_on(store.execute(query))).await??;
    Ok(result.item_count())
}
```
<!-- /snippet -->

`Store` is `Clone` and `'static`, so it moves into the closure; `Handle::block_on` is
allowed on a blocking-pool thread. Use `QueryResult::iter()` there too if decoding is
also expensive. Do not do the same for `transaction` — see below.

## Sharing one instance across tasks

<!-- snippet: rust-shared-instance -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```rust
/// One `Ditto` per process and persistence directory. It is `Send + Sync` but not
/// `Clone`: share it as `Arc<Ditto>`.
#[derive(Clone)]
pub struct AppState {
    pub ditto: Arc<Ditto>,
}

impl AppState {
    pub async fn record_reading(&self, sensor: &str, value: f64) -> Result<(), DittoError> {
        self.ditto
            .store()
            .execute((
                "INSERT INTO readings DOCUMENTS (:doc)",
                serde_json::json!({ "doc": { "sensor": sensor, "value": value } }),
            ))
            .await?;
        Ok(())
    }
}
```
<!-- /snippet -->

This is the shape for axum/tonic state: `Ditto`, `Store`, `QueryResult`, `DittoError`
and the handles are `Send + Sync`, and the `execute` and `open` futures are `Send`, so
handlers that hold them across `.await` compile under `tokio::spawn`.

## Graceful shutdown

Keep the `Ditto` alive until the program is done: dropping it stops sync and shuts the
instance down (the crate README quickstart returns from `main` right after
`sync().start()`, which syncs nothing). A service runs until its shutdown signal:

<!-- snippet: rust-graceful-shutdown -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```rust
/// Runs until `shutdown` resolves (e.g. `tokio::signal::ctrl_c()`), then tears down in
/// order: the subscription guard cancels, then sync stops. The caller drops the last
/// `Arc<Ditto>` afterwards, which shuts the instance down.
pub async fn serve(
    ditto: Arc<Ditto>,
    shutdown: impl std::future::Future<Output = ()>,
) -> Result<(), DittoError> {
    ditto.sync().start()?;
    let subscription = Cancelling::new(ditto.sync().register_subscription("SELECT * FROM cars")?);
    shutdown.await;
    drop(subscription); // cancels
    ditto.sync().stop();
    Ok(())
}
```
<!-- /snippet -->

Call it as `serve(ditto.clone(), async { let _ = tokio::signal::ctrl_c().await; })`.
`Ditto::close(self)` is the same as dropping it, so it only shuts down when you hold
the sole owner: `Arc::into_inner(ditto).map(Ditto::close)` makes that explicit.

## What not to race

These futures are **not cancel-safe**. Dropping them before completion — by
`tokio::time::timeout`, a losing `select!` branch, `JoinHandle::abort`, or a dropped
request future — is a defect, not a cancellation:

| Future | What cancelling it does (executed 5.0.4–5.2.0) |
|---|---|
| `Ditto::open` | Process aborts when the open completes (SIGABRT). |
| `Store::transaction` / `transaction_with_options` | Later transactions never start (hang). |
| `Store::execute` | Nothing: it already finished inside its first poll. |

Await `open` once at start-up, outside any timeout. Bound a transaction's work *inside*
the closure (timeouts on your own I/O, then return `Err` to roll back), never around the
call. Inside a transaction use only `txn.execute`: `ditto.store().execute` there waits
on the transaction that is waiting on it (executed deadlock).

## Runtime flavour and dependencies

- The crate depends on `tokio` with `features = ["full"]` itself; your `Cargo.toml` adds
  what *you* use (`macros`, `rt-multi-thread`, `sync`, `time`).
- `#[tokio::main]` (multi-thread) is the right default. `current_thread` works
  (executed) but every `execute` blocks the only worker.
- `Ditto::open_sync` exists for non-async callers; inside async code it blocks the worker
  for the whole open. Prefer `Ditto::open(config).await`.
- The auth expiration handler is `async`, but Ditto runs it on its own thread inside a
  temporary current-thread runtime ([concurrency.md](concurrency.md#the-auth-expiration-handler)):
  do its work inline and send results out through a channel.

## CAP-07 Sync subscriptions

| API | Shape |
|---|---|
| `ditto.sync.registerSubscription` | `SyncSubscription registerSubscription(String query, {Map<String, dynamic> arguments = const {}})`; synchronous |
| `SyncSubscription` | `queryString`, `queryArguments`, `isCancelled`, `cancel()` (`void`) |
| `ditto.sync.subscriptions` | `Set<SyncSubscription>`, read from the native registry on each access |

From `lib/src/sync.dart` @ `sdk-release-5.2.0`, `sdk-release-5.1.0` and ditto_live
5.0.4. Imports: `package:ditto_live/ditto_live.dart`.

<!-- snippet: flutter-sync-1 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// Syncs the cars of [color] from other peers until the returned
/// subscription is cancelled. A subscription query cannot use LIMIT or
/// ORDER BY: registering one throws.
SyncSubscription subscribeToCars(Ditto ditto, String color) =>
    ditto.sync.registerSubscription(
      'SELECT * FROM cars WHERE color = :color',
      arguments: {'color': color},
    );
```
<!-- /snippet -->

Executed (macOS, debug, 5.0.4, 5.1.0, 5.2.0):

- A new subscription is in `ditto.sync.subscriptions` with its `queryString` and
  `queryArguments`; after `cancel()` it is gone and `isCancelled` is `true`; a second
  `cancel()` is a no-op.
- **Dropping the handle does not cancel it.** A subscription whose handle was discarded
  was still listed in `ditto.sync.subscriptions`, and active, until it was cancelled
  through that set. Keep the handle in the object that owns the data need
  (the repository), and cancel it there.
- After `ditto.close()`, `isCancelled` is `false` on 5.0.4 and `true` on 5.1.0 and
  5.2.0.
- A subscription may be registered before `sync.start()`: the sync-status probe below
  registers it first, then starts sync on both peers.

Register subscriptions once, at startup or when the data need begins, not per screen
build; they are not tied to an observer. Cancel while Ditto is open.

### LIMIT and ORDER BY are rejected

`registerSubscription` throws synchronously, at the call, and registers nothing
(executed, macOS, 5.0.4, 5.1.0 and 5.2.0; the same for `LIMIT 10` and `ORDER BY`):

```text
DittoException(<dql> Unsupported feature: Limit or Order by)
```

A subscription says which documents to sync. Put `LIMIT` and `ORDER BY` in the
observer or `execute` query that renders them, against the local store.

### Sync scopes

Sync scopes are set with DQL `ALTER SYSTEM` through `ditto.store.execute`; there is no
Dart API for them. The statement and the scope values: the `sync-subscriptions` skill
if installed, otherwise <https://docs.ditto.live/sdk/latest/sync/sync-scopes>. Not
executed here.

## CAP-14 Sync status

The Flutter SDK has no sync-status type or stream. What exists:

1. **`QueryResult.commitID`** (`int?`): the local commit that holds a mutating
   statement's writes; `null` for a `SELECT` and inside an uncommitted transaction
   (dartdoc, `execute.dart` @ `sdk-release-5.2.0`; also in 5.0.4 and 4.14.7).
2. **The `system:data_sync_info` collection**, queried through `execute` or an
   observer: one document per peer this one syncs with, with
   `documents.synced_up_to_local_commit_id`, `documents.sync_session_status` and
   `is_ditto_server` (<https://docs.ditto.live/sdk/latest/sync/monitoring-sync-status>,
   which has Dart samples).

```dart
/// Inserts [car] and returns the ID of the local commit that holds it, the
/// only sync-progress value the Flutter SDK exposes.
Future<int?> insertCarCommit(Ditto ditto, Map<String, dynamic> car) async {
  final result = await ditto.store.execute(
    'INSERT INTO cars DOCUMENTS (:car)',
    arguments: {'car': car},
  );
  return result.commitID; // null for a query that changed nothing
}
```
<!-- /snippet -->

<!-- snippet: flutter-sync-3 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// Whether a peer has confirmed every local commit up to [commitID], per the
/// local-only `system:data_sync_info` collection (one document per peer).
Future<bool> isSyncedTo(Ditto ditto, int commitID) async {
  final info = await ditto.store.execute('SELECT * FROM system:data_sync_info');
  return info.items.any((item) {
    final documents = item.value['documents'] as Map<String, dynamic>?;
    final syncedUpTo = documents?['synced_up_to_local_commit_id'];
    return syncedUpTo is int && syncedUpTo >= commitID;
  });
}
```
<!-- /snippet -->

Executed (macOS, debug, two instances in one process over TCP loopback, each run its
own process): each write's `commitID` was larger than the previous one; the writer's
`system:data_sync_info` held one document, for the reader (`_id` its peer key,
`is_ditto_server` `false`, `sync_session_status` `Connected`), and
`synced_up_to_local_commit_id` reached the write's `commitID` on the third poll, 100 ms
apart: 5.0.4 3 of 3 runs, 5.1.0 3 of 3, 5.2.0 1 of 3. **In the other two 5.2.0 runs the
fourth `execute` on `system:data_sync_info` never completed.** The same hang appeared on
all three lines when the poll ran after earlier tests had opened and closed instances in
the same process (5.0.4 1 of 1, 5.1.0 2 of 3, 5.2.0 3 of 5). The cause is not known. So:

- Do not `await` this query on a path the UI waits for, and never in a tight loop.
  Query it every few seconds from a `Timer`, or observe it (the docs' approach; not
  executed here), and show a missing answer as "unknown", not "not synced".
- `.timeout()` on the `Future` stops your wait, not the query; on 5.1.0+ later `execute`
  calls queue behind it on the same worker isolate (source), so a hung status query can
  stall them too (inference; not observed).

What it is not:

- **Not a delivery receipt for the mesh.** A peer's `synced_up_to_local_commit_id`
  says that peer has this peer's commits; it says nothing about peers further away, or
  about whether a remote app has read them.
- No per-document status, no "upload pending" count, no callback when a commit is
  acknowledged: poll the collection or observe it (the docs say observers on it fire
  every 500 ms whether or not it changed).
- `ditto_flutter_tools` 3 removed its `SyncStatus` helpers because subscription timing
  did not reflect sync progress
  (<https://docs.ditto.live/sdk/latest/migration-guides/flutter-v4>).

## CAP-16 Error handling

### Two unrelated families

| Type | Declared as | Meaning | Lines |
|---|---|---|---|
| `DittoException` | `final class DittoException implements Exception` | Ditto rejected the call: bad DQL, bad config, locked directory, invalid state | all |
| `DittoClosedException` | `extends DittoException` | The instance is closed; prints `DittoException(This ditto instance is closed, so all operations are invalid)` | all |
| `DittoEncryptionException` | `extends DittoException`, with `reason` (`DittoEncryptionErrorReason`: `keyRequired`, `keyUnexpected`, `keyInvalid`, `unsupportedScheme`, `metadataCorrupt`) | The store could not be opened for an encryption reason | 5.2.0 |
| `DittoError` | `final class DittoError extends Error` | An internal or unexpected failure: the SDK not initialized, an internal core error, a file that cannot be written | all |

From `lib/src/exception.dart` @ `sdk-release-5.2.0` (5.2.0 also exports the
encryption types; the probes check that the enum values above exist). Native core
errors are mapped by code: codes the core marks as errors become `DittoError`, the rest
`DittoException` (`throwFfi`, same file); `Ditto.open` maps unknown and internal codes
to `DittoError` (`lib/src/bridge/native/open.dart`).

**`DittoError` is not a `DittoException`, and neither is a subtype of the other.** An
`on DittoException` clause does not catch `DittoError`. Name both where you handle
Ditto failures; let anything else propagate. Imports: `dart:developer`,
`package:ditto_live/ditto_live.dart`.

```dart
/// Runs [query] and returns its items, or null when Ditto rejects it.
/// DittoException (a rejected query, a closed instance) and DittoError (an
/// internal failure) are unrelated types, so a handler names each one.
Future<List<Map<String, dynamic>>?> tryQuery(Ditto ditto, String query) async {
  try {
    final result = await ditto.store.execute(query);
    return result.items.map((item) => item.value).toList();
  } on DittoException catch (error) {
    log('query rejected: $error', name: 'ditto');
    return null;
  } on DittoError catch (error, stackTrace) {
    log('Ditto failed', name: 'ditto', error: error, stackTrace: stackTrace);
    rethrow;
  }
}
```
<!-- /snippet -->

Executed (macOS, debug, 5.0.4, 5.1.0, 5.2.0): `tryQuery` returns `[]` for a valid query
on an empty collection and `null` for `SELEC * FROM`.

Two more types come from Dart itself:

- **`ArgumentError`** from `Ditto.open` (5.2.0) when the config holds a value the SDK
  cannot encode, e.g. `systemParameters: {'x': double.infinity}` →
  `Invalid argument(s): System parameter doubles must be finite` (executed, macOS
  5.2.0). An unknown parameter name is a `DittoException` instead (catalogue).
- **`StateError`** from a second `listen` on an observer's `changes`
  ([observers.md](observers.md#when-delivery-starts)).

### Where errors surface

| Call | How it fails |
|---|---|
| `store.execute`, `Transaction.execute`, `Ditto.open`, `newAttachment`, `copyToPath` | The returned `Future` fails; nothing is thrown at the call |
| `sync.start()`, `registerObserver`, `registerSubscription`, `updateTransportConfig` (web) | Thrown synchronously at the call |
| `store.transaction` callback | A throw rolls back and is rethrown from `transaction()` |
| `auth.login` | A rejected login is `AuthResponse.exception`; only a closed instance throws ([connect.md](connect.md#cap-04-authentication-and-identity)) |
| `DittoLogger.exportLogs` on web | `UnsupportedError` thrown synchronously, before any `Future` exists |
| V1 `onChange` callback that throws | Goes to the zone that registered the observer, as an uncaught error (5.2.0 source, `bridge/native/store.dart`) |
| Presence callback that throws | Logged by Ditto, not rethrown (5.2.0 source) |
| Connection request handler that throws | The request is denied (executed) |
| Expiration handler that throws or fails asynchronously | Nothing awaits it: an uncaught async error. On 5.0.4 an unguarded `login` after `close()` failed the test this way (executed) |

All rows without a mark are executed (macOS, debug, 5.0.4 to 5.2.0; the web rows on
Chrome). Because `execute` fails through its `Future`, an un-awaited call loses the
error: the `unawaited_futures` and `discarded_futures` lints catch that.

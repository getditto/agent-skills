## CAP-11 Observers and live queries

| API | Shape | Lines |
|---|---|---|
| `ditto.store.registerObserver` | `StoreObserver registerObserver(String query, {Map<String, dynamic> arguments = const {}, void Function(QueryResult)? onChange})` | all |
| `StoreObserver` | `changes` (single-subscription `Stream<QueryResult>`), `cancel()` (`void`), `isCancelled`, `queryString`, `queryArguments` | all |
| `registerObserverV2`, `registerObserverWithSignalNext` | return `StoreObserverV2`; both `@experimental` | 5.1.0+ |
| `StoreObserverV2` | `changes`, `cancel()`, `isCancelled`, `signalNext()`, `queryString`, `queryArguments` | 5.1.0+ |
| `ditto.store.observers` | `Set<StoreObserver>` of live V1 observers | 5.2.0 |

From `lib/src/store/store.dart` @ `sdk-release-5.2.0` and `sdk-release-5.1.0`, and
ditto_live 5.0.4 from pub.dev. The query must be a `SELECT`:
`registerObserver('DELETE FROM cars')` throws at the call
`DittoException(<dql> Unsupported feature: non-SELECT statement in store observer)`
(executed, macOS, 5.0.4, 5.1.0, 5.2.0).

- **Arguments are named:** `arguments: {'color': 'blue'}`, bound to `:color`. Never
  interpolate values into the query string.
- **`result.items` is an `Iterable<QueryResultItem>`, not a `List`** (executed: it is
  not a `List`). Map and copy it before it reaches widget state:
  `result.items.map((item) => item.value).toList()`.
- **No `ORDER BY` is needed.** A plain `SELECT … WHERE` observer delivers its match
  (executed, all three lines). Add `ORDER BY` only when the screen needs an order.
- Callbacks and `changes` events arrive on the isolate that registered the observer,
  in the zone it was registered in (`lib/src/bridge/native/store.dart` @
  `sdk-release-5.2.0`); with Flutter that is the UI isolate, so keep the work in them
  short ([concurrency.md](concurrency.md#where-each-callback-runs)).

### The default: no onChange, one listener

Register **without** `onChange`, listen to `changes` once, immediately, and cancel the
listener and then the observer while Ditto is open. Imports: `package:ditto_live/ditto_live.dart`.

<!-- snippet: flutter-observers-1 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// Watches the blue cars. [onCars] receives every result as a list. Call the
/// returned function to stop, while Ditto is still open.
Future<void> Function() watchBlueCars(
  Ditto ditto,
  void Function(List<Map<String, dynamic>> cars) onCars,
) {
  // No onChange: an observer that has one also keeps every result buffered
  // in its unlistened `changes` stream (5.0.0 through 5.2.0). Listen to
  // `changes` once, right away; from 5.1.0 an observer without onChange
  // starts on that first listen.
  final observer = ditto.store.registerObserver(
    'SELECT * FROM cars WHERE color = :color',
    arguments: {'color': 'blue'},
  );
  final subscription = observer.changes.listen((result) {
    // `items` is an Iterable; copy it before handing it to the UI.
    onCars(result.items.map((item) => item.value).toList());
  });
  return () async {
    // Cancelling the listener does not cancel a V1 observer; cancel both.
    await subscription.cancel();
    observer.cancel();
  };
}
```
<!-- /snippet -->

An object that outlives one screen holds it the same way. Imports: `dart:async`,
`package:ditto_live/ditto_live.dart`, `package:flutter/widgets.dart`:

<!-- snippet: flutter-observers-2 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// Owns the observer for as long as the data is needed, independent of any
/// one widget. Screens listen to [cars]; [dispose] stops observing.
class CarsRepository {
  CarsRepository(Ditto ditto) {
    // No onChange (it would also buffer every result in the unlistened
    // `changes` stream, 5.0.0 through 5.2.0). This class holds the one
    // `changes` listener, started right away.
    _observer = ditto.store.registerObserver('SELECT * FROM cars');
    _changes = _observer.changes.listen((result) {
      cars.value = result.items.map((item) => item.value).toList();
    });
  }

  final cars = ValueNotifier<List<Map<String, dynamic>>>(const []);
  late final StoreObserver _observer;
  late final StreamSubscription<QueryResult> _changes;

  bool get isObserving => !_observer.isCancelled;

  /// Call while Ditto is still open: the listener first, then the observer.
  Future<void> dispose() async {
    await _changes.cancel();
    _observer.cancel();
    cars.dispose();
  }
}

class CarsScreen extends StatelessWidget {
  const CarsScreen({super.key, required this.repository});

  final CarsRepository repository;

  @override
  Widget build(BuildContext context) => ListenableBuilder(
    listenable: repository.cars,
    builder: (context, _) => Text('${repository.cars.value.length} cars'),
  );
}
```
<!-- /snippet -->

Executed (macOS desktop, debug, Flutter 3.50.0, ditto_live 5.0.4, 5.1.0 and 5.2.0): the
first block delivers the inserted blue car; the repository's screen shows `1 cars` and
survives leaving and re-entering.

### The onChange buffering defect

**An observer registered with `onChange` also keeps every result in its `changes`
stream, and nothing ever drains it.** `StoreObserver` and `StoreObserverV2` add each
`QueryResult` to a single-subscription `StreamController` as well as passing it to
`onChange`; a single-subscription stream with no listener buffers without limit.

- **Lines:** V1 `registerObserver` on 5.0.4, 5.1.0 and 5.2.0; `registerObserverV2`
  and `registerObserverWithSignalNext` on 5.1.0 and 5.2.0.
- **Symptom:** memory that grows with every change to the query's result and is
  released only when the observer is cancelled. No error, no log line.
- **Evidence** (executed, macOS debug, all listed lines): after the initial result and
  five inserts (6 `onChange` calls), a `changes.listen` added afterwards received
  exactly 6 replayed results. In auto mode (`registerObserverV2`) an unlistened stream
  is not paused, so delivery never slows down.
- **Workaround:** the blocks above. Do not pass `onChange`; hold the one `changes`
  subscription. For signal-next, call `observer.signalNext()` after each result,
  also when processing fails.

The 5.2.0 dartdoc of `StoreObserver` warns only that a *late* listener's buffer can
grow, and suggests `onChange` instead; given the defect, do not follow that suggestion.

### When delivery starts

| Line | Observer without `onChange` | With `onChange` |
|---|---|---|
| 5.0.x | Starts at registration; `changes` buffers until listened to | Starts at registration |
| 5.1.0, 5.2.0 | Starts on the first `changes.listen` | Starts at registration |

Executed (macOS, debug): one insert between registration and the first listen; the
listener received item counts `[0, 1]` on 5.0.4 (the initial empty result was buffered)
and `[1]` on 5.1.0 and 5.2.0. On 5.1.0+ an observer that is never listened to never
starts, so listen right away. The first result after the start is the current result,
before sync has delivered anything: `[0]` for an empty collection (executed).

`changes` accepts one listener for the observer's lifetime: a second `listen`
throws a `StateError` whose message is `Stream has already been listened to.`, even after the first
listener was cancelled (executed, all three lines). Hence never a `StreamBuilder` over
`changes`: [anti-patterns.md](anti-patterns.md#streambuilder-over-changes).

### Cancelling

| Action | V1 `StoreObserver` | V2 `StoreObserverV2` (5.1.0+) |
|---|---|---|
| Cancel the `changes` listener | Observer keeps running; `onChange` still fires (executed) | Cancels the observer (executed) |
| `observer.cancel()` | Stops it and closes `changes` | Stops it and closes `changes` |
| `isCancelled` after `ditto.close()` | `false` on 5.0.4, `true` on 5.1.0 and 5.2.0 (executed) | `true` (executed, 5.1.0, 5.2.0) |
| `cancel()` after `ditto.close()` | Throws `DittoClosedException` on 5.0.4 and 4.14.7; a no-op on 5.1.0+ | A no-op |

The last row is from source: 5.0.4 and 4.14.7 `cancel()` read `_ditto.ptr` before
closing the stream; 5.1.0+ return early when `isCancelled`. On every line, the
`changes` stream of an observer still live at `close()` is never closed: `close()` does
not reach the observers' stream controllers (`lib/src/ditto.dart` and
`store/store.dart` @ `sdk-release-5.2.0`), so an `onDone` handler never runs and an
`await for` over `changes` never ends. **Cancel listeners and observers while Ditto is
open**, before `close()`.

Dropping the last Dart reference does not cancel either kind: the live query belongs to
the native store, and on 5.2.0 the `Store` itself keeps every V1 observer in
`ditto.store.observers` until `cancel()` (source; the 5.2.0 probe below shows an
observer whose listener is gone still listed and running).

### Back-pressure: registerObserverWithSignalNext (5.1.0+)

With `registerObserverWithSignalNext` Ditto delivers one result and then waits for
`signalNext()`. Changes made meanwhile are applied to the store and arrive together, as
one result, after the signal; a result equal to the last delivered one is not sent
(dartdoc, `store.dart` @ `sdk-release-5.2.0`). Use it when processing a result takes
longer than the query changes. Imports: `dart:async`, `dart:developer`,
`package:ditto_live/ditto_live.dart`.

<!-- snippet: flutter-observers-4 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// 5.1.0+: hands each result to [render] and asks for the next one only
/// when [render] has finished. Changes made meanwhile arrive together in
/// the next result. [cancel] stops observing; call it while Ditto is open.
class PacedCarsFeed {
  PacedCarsFeed(Ditto ditto, this._render)
    // No onChange: with one, every result is also buffered in the unlistened
    // `changes` stream (5.1.0, 5.2.0). This class holds the one listener.
    // ignore: experimental_member_use
    : _observer = ditto.store.registerObserverWithSignalNext(
        'SELECT * FROM cars',
      ) {
    _changes = _observer.changes.listen(
      (result) => unawaited(_renderThenSignal(result)),
    );
  }

  final Future<void> Function(QueryResult result) _render;
  // ignore: experimental_member_use
  final StoreObserverV2 _observer;
  late final StreamSubscription<QueryResult> _changes;

  Future<void> _renderThenSignal(QueryResult result) async {
    try {
      await _render(result);
    } catch (error, stackTrace) {
      log('render failed', name: 'cars', error: error, stackTrace: stackTrace);
    } finally {
      // Nothing more is delivered until signalNext() is called.
      if (!_observer.isCancelled) _observer.signalNext();
    }
  }

  /// Cancels the listener, and with it the V2 observer.
  Future<void> cancel() => _changes.cancel();
}
```
<!-- /snippet -->

Executed (macOS, 5.1.0 and 5.2.0; and Chrome, debug, 5.1.0 and 5.2.0): item counts
`[0]`, nothing for 2 s after three inserts while the first render was unfinished, then
exactly `[0, 3]` after it ended by throwing. **Forgetting `signalNext()` stops delivery
for good, silently.** Pausing the `changes` stream of a signal-next observer has no
effect except a logged warning (source).

The migration guide says the Flutter SDK has no `signalNext`
(<https://docs.ditto.live/sdk/latest/migration-guides/flutter-v4#back-pressure>); that
is wrong from 5.1.0, as the executed run shows.

### registerObserverV2 (5.1.0+)

`registerObserverV2` signals automatically after each result, and honours
`pause()`/`resume()` on its `changes` subscription. Cancelling the listener cancels the
observer, so the subscription is the whole cleanup. Both V2 methods are
`@experimental` (`package:meta`): each use needs `// ignore: experimental_member_use`
under `flutter analyze --fatal-infos`, and their shape may change
([preview.md](preview.md#cap-20-preview-apis)). Imports: `dart:async`,
`package:ditto_live/ditto_live.dart`.

<!-- snippet: flutter-observers-3 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// 5.1.0+: a V2 observer stops when its stream listener is cancelled, so
/// cancelling the subscription is the whole cleanup.
class CarsFeed {
  CarsFeed(Ditto ditto, void Function(List<Map<String, dynamic>> cars) onCars)
    // ignore: experimental_member_use
    : _observer = ditto.store.registerObserverV2('SELECT * FROM cars') {
    _subscription = _observer.changes.listen((result) {
      onCars(result.items.map((item) => item.value).toList());
    });
  }

  // ignore: experimental_member_use
  final StoreObserverV2 _observer;
  late final StreamSubscription<QueryResult> _subscription;

  bool get isActive => !_observer.isCancelled;

  /// Cancels the listener, and with it the V2 observer.
  Future<void> cancel() => _subscription.cancel();
}
```
<!-- /snippet -->

Executed (macOS, 5.1.0 and 5.2.0): after the first result, `cancel()` on the feed turns
`isActive` false. Prefer V1 for code that must also build against 5.0.x, and in apps
you hot-restart (below).

### Finding leaked observers (5.2.0)

`ditto.store.observers` lists every V1 observer not yet cancelled, including one whose
`changes` listener is gone; V2 observers are not in it; after `close()` it is empty.
Imports: `dart:developer`, `package:ditto_live/ditto_live.dart`.

<!-- snippet: flutter-observers-5 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// 5.2.0+: logs every V1 observer that has not been cancelled, including
/// ones whose `changes` listener is gone. Call it to look for leaks; returns
/// their queries.
List<String> logLiveObservers(Ditto ditto) {
  final queries = [
    for (final observer in ditto.store.observers) observer.queryString,
  ];
  log('${queries.length} live observer(s): $queries', name: 'ditto');
  return queries;
}
```
<!-- /snippet -->

Executed (macOS, 5.2.0): after its listener was cancelled the observer was still
listed and `isCancelled` was `false`; after `cancel()` the list was empty.

### Hot restart

A hot restart orphans the running instance and its observers. When a remote change then
reaches an orphaned observer the app can crash with `EXC_BAD_ACCESS` on a
`live query callback` thread (executed, macOS debug, one `flutter run` per run):

| Line | V1 `registerObserver` | V2 |
|---|---|---|
| 5.0.4 | no crash, 0/3 | no API |
| 5.1.0 | crash, 3/3 | crash, 4/4 |
| 5.2.0 | no crash, 0/3 | crash, 4/4 |

V1 delivers through a port on 5.0.4 and 5.2.0 and through a `NativeCallable` on 5.1.0;
V2 always uses a `NativeCallable` (source, `lib/src/bridge/native/store.dart`). The
re-open after the restart fails on every line anyway. Setup and the debug-only
workaround: [widget-integration.md](widget-integration.md#hot-restart).

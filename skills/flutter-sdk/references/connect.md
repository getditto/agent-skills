## CAP-03 Connecting

Import `package:ditto_live/ditto_live.dart`. The pieces, from
`sdks/flutter/ditto_live/lib/src/ditto_config.dart` and `ditto.dart` @ `sdk-release-5.2.0`:

| API | Shape |
|---|---|
| `DittoConfig` | `const DittoConfig({String? databaseID, DittoConfigConnect connect, String? persistenceDirectory, DittoConfigExperimental experimental, Map<String, Object> systemParameters})`. Every field is optional; `systemParameters` is 5.2.0 only |
| `DittoConfigConnectServer` | `const DittoConfigConnectServer({required String url})`: sync with a Ditto server |
| `DittoConfigConnectSmallPeersOnly` | `const DittoConfigConnectSmallPeersOnly({String? privateKey})`: no server; the default `connect` |
| `Ditto.init` | `static Future<void> init({String? wasmUrl, String? wasmShimUrl})`; memoized; the URLs matter on web only ([web.md](web.md#asset-loading)) |
| `Ditto.open` | `static Future<Ditto> open([DittoConfig config = const DittoConfig()])`, positional |
| `Ditto.openSync` | `factory Ditto.openSync([DittoConfig config])`; needs `await Ditto.init()` first on every line |

`databaseID` and `url` are the portal's **Database ID** and **URL** under *Connect via
SDK*, copied verbatim (<https://docs.ditto.live/cloud/portal/getting-sdk-connection-details>).
The default `databaseID` is `00000000-0000-0000-0000-000000000000`. A small-peers-only
instance needs an offline license before it syncs:
`ditto.setOfflineOnlyLicenseToken(license)` (every fixture run does this). It is
synchronous and verifies the token, throwing when verification fails
(`ditto.dart:252-260` @ `sdk-release-5.2.0`; an invalid token was not tried on native).
On web one invalid token did not throw: [web.md](web.md#web-differences).

`Ditto.open` throws `ArgumentError` for a config value Dart cannot encode and
`DittoException` when Ditto rejects the config or the directory is already locked
(dartdoc, `ditto.dart:175-180` @ `sdk-release-5.2.0`).

### Open, configure, close on failure

Open once, configure, and close the instance again if configuring fails, so a failed
start does not leave the directory locked. This service is the one
[widget-integration.md](widget-integration.md) builds on. Executed (macOS, debug, 5.0.4,
5.1.0, 5.2.0, **with Ditto logging disabled in the harness**): `configure` throwing
rethrows, and a second open of the same directory then succeeds, so the failed instance
was closed. That second open is the probe's check, not a recovery path: re-opening in one
process is the hazard under [Shutdown and ownership](#shutdown-and-ownership). After a
failed open or configure, let `close()` run, surface the error, and have the user
relaunch the app; do not retry `DittoService.open` in-process.
The block needs `package:ditto_live/ditto_live.dart` and `package:flutter/widgets.dart`;
`CarsApp` is in widget-integration.md.

<!-- snippet: flutter-widgets-1 -->

```dart
/// Owns the app's one Ditto instance. Open it once, before runApp; close it
/// only when the app exits.
class DittoService {
  DittoService._(this.ditto);

  final Ditto ditto;

  /// Opens Ditto, then runs [configure]: the license or expiration handler,
  /// transports, sync.start(). If [configure] throws, the instance is closed
  /// again, so its persistence directory is not left locked.
  static Future<DittoService> open({
    DittoConfig config = const DittoConfig(),
    required Future<void> Function(Ditto ditto) configure,
  }) async {
    // Required on 5.0.x, automatic from 5.1.0; memoized.
    await Ditto.init();
    final ditto = await Ditto.open(config);
    try {
      await configure(ditto);
    } catch (_) {
      await ditto.close();
      rethrow;
    }
    return DittoService._(ditto);
  }

  /// Closes Ditto. Cancel observers first, while it is still open.
  Future<void> close() => ditto.close();
}

/// The app's entry point, e.g.
/// `Future<void> main() => startCarsApp(configureDitto);`
/// Pass [config] only to change the connect mode or, in debug builds, the
/// directory; an app keeps the SDK default persistence directory.
Future<void> startCarsApp(
  Future<void> Function(Ditto ditto) configure, {
  DittoConfig config = const DittoConfig(),
}) async {
  WidgetsFlutterBinding.ensureInitialized();
  final service = await DittoService.open(config: config, configure: configure);
  runApp(CarsApp(service: service));
}
```
<!-- /snippet -->

Give `configure` the identity step for the connect mode, then transports, then
`ditto.sync.start()`: for a server, `startServerSync` in
[CAP-04](#cap-04-authentication-and-identity); for small peers only,
`setOfflineOnlyLicenseToken`, then the transports
([transports.md](transports.md#cap-06-customizing-transports)), then `sync.start()`.

### Persistence directory

- **Pass no `persistenceDirectory` in an app.** The SDK default is `ditto-{databaseID}`
  (lowercase) under `Ditto.defaultRootDirectory`: Application Support on 5.2.0,
  Documents on 5.0.x and 5.1.x. 5.2.0 opens an existing 5.1.0 Documents store in place
  (executed on macOS and the iOS Simulator: same path, same documents). Details:
  [versions.md](versions.md).
- A relative path resolves against `Ditto.defaultRootDirectory`; the absolute result is
  `ditto.absolutePersistenceDirectory` (dartdoc, `ditto_config.dart` @ `sdk-release-5.2.0`).
- Two live instances on one directory fail. Executed (macOS, 5.2.0):
  `DittoException(File already locked, working dir = …/ditto-00000000-0000-0000-0000-000000000000,
  retried 5 times. Multiple Ditto instances cannot run at the same time within the same
  working directory. …)`.
- On web there is no directory: the store is in memory
  ([web.md](web.md#in-memory-store-and-reload)).

### Initialization mistakes

Each re-checked against `sdk-release-5.2.0` source and the fixture:

| Wrong | Right | Evidence |
|---|---|---|
| `Ditto.open(identity: …)` | `Ditto.open(DittoConfig(…))`: positional, no identity class in v5 | source, `ditto.dart:182` |
| `DittoConfig(databaseId: …)` | `databaseID`, capital `ID` | source, `ditto_config.dart:31` |
| `Authenticator.developmentProvider(…)` | a static `String` getter: `provider: Authenticator.developmentProvider` | executed in the login probe |
| `ditto.auth?.…` | `ditto.auth` is non-nullable (also `store`, `sync`, `presence`) | source, `ditto.dart:117-127` |
| `sync.start()` before the expiration handler, with a server config | `await ditto.auth.setExpirationHandler(…)` first | executed: throws, see CAP-04 |
| `Ditto.open` in a widget's `initState` | open once before `runApp` | a second open of the directory fails, see above |
| Skipping `await Ditto.init()` because `open` calls it | call it unconditionally: 5.0.x `open` does not | source below |

On 5.0.4, `Ditto.open` without a prior `Ditto.init()` throws `DittoError(Ditto not
initialized. Call `Ditto.init()` and await the `Future` before using any Ditto
functionality)` (`lib/src/ditto.dart:134,289`, ditto_live 5.0.4 from pub.dev). The same
string is thrown by a `DittoLogger` getter before init on 5.0.4, 5.1.0 and 5.2.0 (executed).

## CAP-04 Authentication and identity

Server connections need an **expiration handler before `sync.start()`**. Without one,
`sync.start()` throws synchronously and `sync.isActive` stays `false` (executed, macOS
debug, 5.0.4, 5.1.0 and 5.2.0, the same text on each):

```text
DittoException(<authentication> The operation failed because an authentication expiration handler has not yet been set.)
```

<!-- snippet: flutter-connect-1 -->
<!-- Generated by scripts/sync-snippets.py from code CI runs. Edit the marked source, not this block. -->
```dart
/// Starts sync against a Ditto server. [fetchToken] returns a token from your
/// identity provider. With a server connect config, sync.start() throws
/// DittoException unless an expiration handler is set first.
Future<void> startServerSync(
  Ditto ditto,
  Future<String> Function() fetchToken,
) async {
  await ditto.auth.setExpirationHandler((ditto, timeUntilExpiration) async {
    // The handler can run after close() (seen on 5.0.4); login() would
    // throw DittoClosedException.
    if (ditto.isClosed) return;
    try {
      final response = await ditto.auth.login(
        token: await fetchToken(),
        provider: 'REPLACE_ME_WITH_YOUR_PROVIDER',
      );
      // A rejected login is reported here, not thrown.
      final error = response.exception;
      if (error != null) log('Ditto login failed: $error', name: 'auth');
    } catch (error) {
      // Thrown: fetchToken() failed, or Ditto closed while logging in.
      log('Ditto login threw: $error', name: 'auth');
    }
  });
  ditto.sync.start();
}
```
<!-- /snippet -->

Imports: `dart:developer` (`log`) and `package:ditto_live/ditto_live.dart`.

- **`setExpirationHandler` is an async method, not a property.** Await it. The handler
  type is `void Function(Ditto ditto, Duration timeUntilExpiration)`; an `async`
  handler is allowed, but nothing awaits it.
- **`login({required String token, required String provider})` returns
  `Future<AuthResponse>`.** A rejected login is `response.exception`, not a throw
  (executed against an unreachable server, all three lines:
  `DittoException(Error logging in. Status code 1. Client info: null)`). It does throw
  `DittoClosedException` once the instance is closed: on 5.0.4 the handler ran after
  `close()` and the unguarded `login` failed the test, hence the `isClosed` check and
  the `try`.
- `provider` is your identity provider's name from the portal;
  `Authenticator.developmentProvider` is the development provider.
- **`logout`:** 5.0.x `logout()` only logs out; 5.1.0 also stops sync; 5.2.0
  `logout({cleanup})` stops sync, then awaits `cleanup(ditto)`, logging rather than
  rethrowing its errors (`lib/src/auth.dart` @ `sdk-release-5.2.0`, `sdk-release-5.1.0`,
  ditto_live 5.0.4). Not executed.
- **Status:** `ditto.auth.status` (`isAuthenticated`, `userID`) is a snapshot; 5.2.0 has
  no status stream (source).
- A small-peers-only instance never calls the handler; `ditto.auth` still exists.

Permission rules and token claims are concept material:
<https://docs.ditto.live/sdk/latest/auth-and-authorization/cloud-authentication> and
<https://docs.ditto.live/sdk/latest/auth-and-authorization/data-authorization>.

## CAP-05 Lifecycle

- `ditto.sync.start()` and `ditto.sync.stop()` are synchronous and return `void`; each is
  a no-op when already in that state; `ditto.sync.isActive` reports it (dartdoc,
  `sync.dart:38-56` @ `sdk-release-5.2.0`). `start()` throws `DittoException` for a
  server config without a handler (above) and, on web 5.2.0, for an enabled
  peer-to-peer transport ([web.md](web.md#web-differences)).
- `Future<void> close()` is idempotent (executed: a second call returns). Afterwards
  `store.execute` returns a Future that fails with `DittoClosedException`, while
  `sync.start()` and `store.registerObserver` throw it at the call (executed, all three
  lines). `close()` does not wait for calls already in flight; they fail on their next
  use of the instance (source comment, `ditto.dart:305-307`).

/// Closes Ditto when the app shuts down. close() is idempotent: calling it

Future<void> shutDownDitto(Ditto ditto) async {

}

### Cancel, stop, close

| Handle | Call | Returns | Notes |
|---|---|---|---|
| `StoreObserver` (V1) | `cancel()` | `void` | Cancelling its `changes` listener does **not** cancel it (executed). After `close()`: a no-op on 5.1.0+, throws `DittoClosedException` on 5.0.4 (source: 5.0.4 `cancel` reads `ditto.ptr`) |
| `StreamSubscription` on `changes` | `cancel()` | `Future<void>` | Cancel it before the observer, while Ditto is open |
| `StoreObserverV2` (5.1.0+) | cancel the `changes` subscription, or `cancel()` | `Future<void>` / `void` | Cancelling the listener cancels the observer (executed, [observers.md](observers.md#cap-11-observers-and-live-queries)) |
| `SyncSubscription` | `cancel()` | `void` | |
| `PresenceObserver` | `stop()` | `void` | `stop`, not `cancel` |
| `AttachmentFetcher` | `stop()` | `void` | |
| `TransportConditionsObserver` (5.1.0+) | `stop()` | `void` | Also stopped by `close()` |
| sync | `ditto.sync.stop()` | `void` | The instance stays open |
| `Ditto` | `close()` | `Future<void>` | Await it |

`isCancelled` of a V1 observer turns `true` on `close()` on 5.1.0 and 5.2.0 and stays
`false` on 5.0.4 (executed).

### Shutdown and ownership

- **One instance for the app's lifetime.** Open it before `runApp` and pass it down
  ([widget-integration.md](widget-integration.md)). Do not close and re-open Ditto in
  one process to "reset" it: with Ditto logging on, a native handle from the closed
  instance finalized later by the garbage collector aborted the process
  (`EXC_CRASH (SIGABRT)`, 3 of 3 runs, 5.0.4) or deadlocked it (5.1.0 3 of 3, 5.2.0
  2 of 3) on macOS debug; `await close()` did not prevent it. Do not disable logging
  to avoid it; keep one instance.
- **`await ditto.close()` before the process exits**, after cancelling observers. Never
  in `State.dispose()` (it is synchronous and runs on every unmount) and never on
  pause: a paused app can resume. Close from `AppLifecycleListener.onExitRequested`,
  which Flutter calls only for exits the platform lets the app cancel (its docs name
  macOS and Linux); iOS and Android end the process without one
  ([widget-integration.md](widget-integration.md#app-lifecycle)).
- **Hot restart** does not close the instance and leaves its directory locked:
  [widget-integration.md](widget-integration.md#hot-restart).
